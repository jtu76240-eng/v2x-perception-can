# V2X 프로젝트의 객체·차선 인식 및 CAN 송신

TOPST AI-G 보드에서 TCNN 기반 객체 인식과 OpenCV 기반 차선 인식을 수행하고, 결과를 중앙 제어용 D3-G 보드에 CAN으로 전달하는 프로그램입니다.

텔레칩스 차량용 반도체 임베디드 SW 스쿨 3기 2차 프로젝트에서 담당한 인식·통신 부분을 정리했습니다. 전체 프로젝트는 5인 팀으로 진행했으며, 중앙 제어와 차량·인프라 간 통신 코드는 이 저장소에 포함하지 않습니다.

관련 프로젝트: 1차 V2V 프로젝트의 인식·UART 코드는 [v2v-perception-uart](https://github.com/jtu76240-eng/v2v-perception-uart)에 있습니다.

## 프로젝트와 담당 범위

- 프로젝트명: 능동형 위기 대응 및 V2X 통신 기반의 사고 정보 전파 시스템
- 기간: 2026.01.12~2026.02.13
- 팀 성과: 2차 프로젝트 우수 프로젝트상 수상
- 정리 기준: `main` 브랜치

제공된 TCNN 앱을 기반으로 다음 기능을 추가·수정했습니다.

- 단일 객체 인식 모델을 두 NPU에서 활용하도록 추론 실행 흐름 변경
- 카메라 영상을 공유 메모리로 전달하고, 별도 Python 프로세스에서 차선 인식 수행
- 차선 판단 결과를 공유 메모리에 기록하고 CAN 송신 모듈과 연동
- 객체·차선 메시지에 시각, 카운터, 자체 검증값을 구성해 SocketCAN으로 송신
- 영상 회전, 선택적 비동기 녹화 및 빌드·배포·실행 스크립트 추가

프로젝트에서는 Yocto 커널·DTB를 Ubuntu에 이식해 CAN 인터페이스를 활성화하고, `cansend`와 `candump`로 중앙 제어용 D3-G 보드와 송수신을 확인했습니다. CAN은 프로젝트 진행 중 별도로 학습해 적용했습니다. 커널·DTB와 해당 설정 자료는 이 저장소에 포함하지 않습니다.

## 원본 코드와 변경 범위

카메라 입력, 스케일러, NPU 추론 및 기존 출력 기능은 제공된 TCNN 앱을 기반으로 합니다. 이 저장소 전체를 새로 작성한 것은 아닙니다.

원본은 두 NPU에서 서로 다른 모델을 병렬 실행하는 구조였습니다. 프로젝트에서는 객체 인식 모델 하나를 사용하므로, 같은 모델을 두 네트워크에 설정하고 프레임을 번갈아 처리하도록 수정했습니다. 추론 시작·대기 함수와 네트워크별 결과 처리도 변경했습니다.

별도 차선 인식 프로세스와 공유 메모리 연동, CAN 송신 기능을 추가했습니다. 코드 구조 변경에 따른 성능 향상 수치는 이 README에서 제시하지 않습니다.

## 실행 구조

객체 인식은 C/C++ 프로그램인 `tcnnapp`에서, 차선 인식은 별도 Python 프로세스에서 수행합니다.

1. `tcnnapp`이 카메라 영상을 받아 모델 입력과 공유 영상으로 준비합니다.
2. 객체 인식 결과 중 신뢰도가 가장 높은 객체 하나를 선택해 CAN 메시지로 송신합니다. 검출 결과가 없으면 미검출 상태를 송신합니다.
3. 영상은 BGR 형식으로 변환해 `/nn_frame_export` 공유 메모리에 기록합니다.
4. `lane_tuning.py`가 새 프레임을 읽어 차선을 판단하고 `/lane_status` 공유 메모리에 결과를 기록합니다.
5. `tcnnapp` 내부의 차선 송신 스레드가 새 차선 결과를 읽어 CAN 메시지로 송신합니다.

영상 공유 메모리는 32바이트 헤더와 두 영상 버퍼로 구성합니다. 차선 결과 공유 메모리는 24바이트이며, 식별값·차선 상태·프레임 번호·결과 기록 시각을 담습니다.

차선 인식에는 영상 전처리, 노란선·흰선 마스크, 원근 변환, 슬라이딩 윈도우 탐색 및 곡선 피팅을 사용합니다. 시험 도로의 중앙선·점선·실선 조합을 기준으로 차선 상태를 판단합니다.

## 실행 환경과 방법

필요한 환경은 다음과 같습니다.

- TOPST AI-G 보드와 해당 환경에서 사용할 수 있는 카메라
- 프로젝트에서 구성한 Ubuntu 실행 환경 및 활성화된 `can0` 인터페이스
- TCNN 런타임, 모델 파일과 관련 보드 라이브러리
- 호스트 PC의 텔레칩스 교차 컴파일 SDK, CMake 및 커널 헤더
- C/C++용 OpenCV와 Python 3, NumPy, Python OpenCV
- CAN 트랜시버, 배선·종단저항 및 상대 보드와 일치하는 통신 설정

이 저장소에는 모델, SDK, TCNN 런타임, 커널·DTB 및 전체 설치 환경이 포함돼 있지 않습니다.

### 호스트 PC에서 빌드·배포

`build.sh`의 `SDK_ENV`, `KERNEL_DIR`를 설치 환경에 맞게 확인합니다. `deploy.sh`의 `SCP_TARGET`, `SCP_PATH`, `SDK_SYSROOT`도 대상 보드와 SDK 위치에 맞게 설정합니다.

```bash
bash build.sh
bash deploy.sh
```

배포 스크립트는 모델과 TCNN 런타임 전체를 설치하지 않으므로, 필요한 실행 파일과 라이브러리를 별도로 준비해야 합니다.

### 보드에서 실행

같은 모델을 두 NPU에서 사용하려면 두 네트워크의 모델 경로를 동일하게 지정합니다. `run.sh`는 기본적으로 `-n`만 지정하므로, 다음처럼 `-n`과 `-N`에 실제 모델 디렉터리를 명시합니다.

```bash
# 객체 인식과 CAN 송신 실행: 경로는 실제 모델 위치로 변경
bash run.sh -n /actual/path/yolov8s_quantized -N /actual/path/yolov8s_quantized
```

다른 터미널에서 차선 인식을 실행합니다.

```bash
bash run_lane_tuning.sh
```

`run_lane_tuning.sh`는 화면 표시를 끄고 실행합니다. 화면에서 차선 파라미터를 조정하려면 그래픽 환경에서 다음과 같이 실행합니다.

```bash
python3 lane_tuning.py --no-record
```

`tcnnapp`에서 공유 영상을 내보내기 전에 차선 프로그램을 실행하면 공유 메모리 연결에 실패할 수 있으므로, 객체 인식 프로그램을 먼저 실행합니다. `run_lane_tuning.sh`의 라이브러리 경로는 프로젝트 당시 Python 3.10 환경을 기준으로 하며, 사용 환경에 맞게 확인해야 합니다.

## CAN 메시지

`src/NnCan.c`는 `can0`에 바인딩한 SocketCAN 소켓을 사용합니다. 객체 메시지 ID는 `0x30`, 차선 메시지 ID는 `0x80`이며, 데이터 길이는 모두 8바이트입니다.

| 바이트 | 내용 |
| --- | --- |
| 0 | 객체 또는 차선 상태값 |
| 1 | 예약값 0 |
| 2~3 | 첫 번째 시각값의 밀리초 하위 16비트, 리틀 엔디언 |
| 4~5 | 송신 직전 시각값의 밀리초 하위 16비트, 리틀 엔디언 |
| 6 | 메시지 종류별 8비트 카운터 |
| 7 | 데이터와 고정 키를 이용해 계산한 자체 검증값 |

- 객체 상태: 미검출 0, 라바콘(클래스 ID 5) 2, 그 외 검출 클래스 1입니다. 클래스와 전송값의 의미는 아래 '객체 클래스와 전송값'에 정리했습니다.
- 차선 상태: 미확정 0, 1차선 1, 1·2차선 사이 2, 2차선 3, 2·3차선 사이 4, 3차선 5입니다.
- 객체의 첫 번째 시각은 프레임 획득 함수가 반환된 뒤 단조 증가 시계로 기록한 시각입니다. 카메라 센서의 촬영 시각은 아닙니다.
- 차선의 첫 번째 시각은 Python 프로그램이 차선 결과를 공유 메모리에 쓸 때 단조 증가 시계로 기록한 시각입니다.
- 송신 직전 시각은 단조 증가 시계로 기록합니다. 첫 번째 시각과 같은 시계를 쓰므로 두 값의 차(16비트 순환 뺄셈)로 지연을 계산할 수 있습니다. 객체 메시지는 프레임 획득부터 송신 직전까지, 차선 메시지는 차선 결과 기록부터 송신 직전까지의 지연입니다. 약 65초를 넘는 지연은 구분할 수 없습니다.
- 첫 번째 시각은 1차 V2V에서 송신 시각만 보내 수신 측이 인식 결과가 오래됐는지 알 수 없었던 점을 반영해 넣었습니다. 중앙 보드 담당자에 따르면 중앙 보드는 이 값으로 중복되거나 오래된 메시지를 걸러내도록 처리했습니다.
- 자체 검증값은 프로젝트에서 사용한 계산 규칙이며, 데이터 암호화나 표준 암호학적 메시지 인증을 구현한 것은 아닙니다.

수신 측은 동일한 상태 매핑과 메시지 규칙을 사용해야 합니다. 이 저장소에는 중앙 제어 보드의 수신·검증·제어 코드가 포함되지 않습니다.

### 객체 클래스와 전송값

사용 모델은 7개 클래스를 학습한 커스텀 YOLO 모델입니다. 클래스는 고속도로 낙하물 조사 자료를 참고해 정했습니다. 가장 많은 공사 자재에서 4개(H-beam, coil, pallet, rubber_cone), 차량 부속 대표로 타이어(tire), 사고 처리 중인 사람(human), 로드킬 대표로 고라니(deer)를 골랐습니다.

2차 프로젝트에서는 1차와 같은 7개 클래스 모델에 1차 시험 중 촬영한 빈 도로 영상과 장애물이 있는 도로 영상을 추가 학습한 뒤 NPU용으로 양자화해 사용했습니다. 1차에서 주행 중 빈 도로를 낮은 신뢰도(약 0.3~0.5)로 장애물이라고 인식하는 경우가 간혹 있어, 모델을 다시 변환하는 김에 빈 도로 데이터를 넣었습니다.

| 전송값 | 클래스 | 의미 |
| --- | --- | --- |
| 0 | — | 미검출 |
| 1 | H-beam, coil, pallet, tire, human, deer | 긴급 제동 대상 장애물 |
| 2 | rubber_cone (클래스 ID 5) | 트럭 등에서 떨어진 유실물로 가정. 충돌해도 차량 손상이 작아 긴급 제동 대상에서 제외 |

전송값에 따른 제동 판단은 중앙 제어 보드에서 수행하며, 이 저장소에는 포함되지 않습니다.

## 실제 시험과 확인 결과

프로젝트 당시 보드에서 수행한 시험과 확인한 결과입니다. 로그와 캡처는 남아 있지 않아 과정을 글로 정리했습니다.

| 시험·문제 | 확인 과정과 결과 |
| --- | --- |
| 보드 간 CAN 양방향 송수신 | AI-G와 중앙 제어용 D3-G에서 서로 `cansend`·`candump`로 양방향 송수신 확인 |
| CAN 수신 데이터가 0으로만 나타남 | 양방향 시험에서 D3-G→AI-G는 아무것도 수신되지 않았고, AI-G→D3-G는 데이터가 0으로만 수신됨<br>↳ AI-G의 CAN TX 신호를 로직 애널라이저로 계측해, 0으로 채워진 프레임이 컨트롤러에서부터 나가는 것을 확인<br>↳ 전송 경로가 아닌 보드 설정으로 범위를 좁혀, 디바이스 트리에서 메시지 RAM 설정이 빠진 것을 확인<br>↳ 설정 보완 후 재빌드하고, 같은 양방향 시험에서 의도한 데이터 송수신 확인 |
| 전방 장애물 인식 확인 | 차량 장착 전에는 책상 위에서 카메라 앞에 장애물을 두고, 장착 후에는 시험 도로에서 화면의 인식 결과 확인 |
| 빈 도로의 장애물 오검출 | 빈 도로 영상을 추가 학습한 뒤 2차 시험과 영상 촬영 중에는 잠깐 떴다 사라지는 정도로, 1차보다 눈에 띄게 줄어듦 |
| 차선 상태값 확인 | 차선 위와 차선 사이에서 차선 메시지 상태값이 위치에 맞게 나오는지 확인 |
| 반사광의 차선 오인식 | 천장 조명이 반사된 바닥 위치가 흰 선으로 인식됨<br>↳ 해당 위치의 RGB가 흰 선 색상 범위 안에 들어오는 것을 확인<br>↳ 범위를 좁히자 실제 차선도 검출되지 않아, 색상 범위 조정만으로는 구분하기 어려운 조건으로 판단 |
| 잘못된 검증값의 수신 처리 | 당시 시험하지 않은 항목. 수신 측이 검증값이 틀린 프레임을 걸러내는지는 확인하지 못함 |

## 적용 범위와 개선할 부분

- 차선 인식은 시험 도로를 대상으로 하며, 일반 도로 전체에 대한 정확도를 검증하지 않았습니다.
- 차선 탐색에서 영상 구역 번호를 탐색 창 번호로 직접 사용하는 부분은 두 번호의 대응 관계를 정리할 필요가 있습니다.
- 차선 검출 실패 시 이전 결과를 최대 9회 유지합니다. 유지 시간은 차선 처리 주기에 따라 달라집니다.
- 영상·차선 공유 메모리의 읽기와 쓰기 사이에 명시적인 프로세스 간 잠금이 없어, 읽는 중 데이터가 갱신되는 상황에 대한 검토가 필요합니다.
- CAN 송신 실패 시 객체·차선 메시지 재시도와 소켓 복구 처리가 충분하지 않습니다.
- 인식 결과의 유효기간 관리가 개선 대상입니다.
- 시각 기준은 프로젝트 종료 후 단조 증가 시계로 통일했으며, 이 변경은 실제 보드에서 검증하지 않았습니다.
- 왜곡 보정 코드는 포함돼 있지만 현재 `CMakeLists.txt`에서 `USE_FISHEYE_UNDISTORT`가 비활성화돼 있습니다. 보정을 켜면 AI-G의 CPU(Cortex-A53)에서 처리 속도가 눈에 띄게 느려져, 보정하지 않은 영상을 기준으로 차선 파라미터를 맞춰 사용했습니다.
- 프로그램 시작 시 실행 파일 옆 `outputs/` 폴더의 기존 파일을 삭제하는 코드가 있습니다. 필요한 영상은 실행 전에 별도로 보관해야 합니다.
